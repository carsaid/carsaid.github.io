# 1高级HTTP请求走私

在本节中，我们将以你目前所学的概念为基础，并教你一些更高级的 HTTP 请求走私 (opens new window)技术。我们还将介绍各种基于 HTTP/2 的攻击，这都要归功于 Burp 独特的 HTTP/2 测试功能 (opens new window)。如果你不熟悉 HTTP/2，请不要担心 - 我们将逐步介绍所有基础知识。

具体而言，我们将看到：

  • 常见的 HTTP/2 实现，是如何为请求走私提供一系列强大的新载体 (opens new window)的，使许多以前安全的站点容易受到此类攻击。
  • 如何使用请求走私来持久地毒害响应队列 (opens new window)，从而有效地实现全站点接管。
  • 如何使用 HTTP/2 专用输入来构建高严重性漏洞，即使目标在前端和后端服务器之间根本不会复用连接 (opens new window)。

为了帮助你练习所学知识，我们在整个过程中提供了故意易受攻击的实验室。这些漏洞是基于我们的研究总监 James Kettle (opens new window) 在 Black Hat USA 2021 上首次提出的真实漏洞。

# 2HTTP/2请求走私

在本节中，我们将向你展示 - 与普遍的看法相反，实施 HTTP/2 实际上使许多网站更容易受到请求走私的影响，即使它们以前可以免受此类攻击。

# 2.1HTTP/2消息长度

从根本上说，请求走私实际上是 利用不同服务器之间 在解释请求长度时的差异。HTTP/2 引入了一个单一的、健壮的机制来实现这一点，长期以来，人们一直认为它对请求走私具有天生的免疫力。

尽管你不会在 Burp 中看到这一点，但 HTTP/2 消息其实是作为一系列单独的 “帧” 来通过网络发送的。每个帧的前面都有一个显式的长度字段，该字段告诉服务器要读入的确切字节数。因此，请求的长度是其帧长度的总和。

从理论上讲，这种机制意味着，只要网站端到端使用 HTTP/2，攻击者就没有机会引入请求走私所需的模糊性。然而，在野外，由于 HTTP/2 降级的广泛且危险性，情况往往并非如此。

# 2.2HTTP/2降级

HTTP/2 降级是使用 HTTP/1 语法重写 HTTP/2 请求，以生成等效 HTTP/1 请求的过程。在与仅支持 HTTP/1 的后端服务器通信时，Web 服务器和反向代理经常这样做，以便向客户端提供 HTTP/2 支持。这种机制是本节中许多攻击的先决条件。

关于HTTP/2消息展示的说明

由于 HTTP/2 是一种二进制协议，因此我们在这些材料中增添了一些艺术性，以人类可读的格式来表示 HTTP/2 消息：

  • 我们将每条消息显示为单个实体，而不是单独的 “帧”。
  • 我们使用 纯文本名称和值字段 来显示标题。
  • 我们在伪标头的名称前面加上冒号，这有助于将它们与普通标头区分开来。
  • 这与 Burp 在 Inspector 中表示 HTTP/2 消息的方式非常相似，但请注意，它们在网络上的实际模样并不像我们所展示的这样。

# 2.3H2.CL漏洞

HTTP/2 请求不会在标头中显式指定其长度。这意味着在降级过程中，前端服务器通常会添加 HTTP/1 的Content-Length标头，并使用 HTTP/2 的内置长度机制 (opens new window)来获取其值。但有趣的是，HTTP/2 请求还可以包含自己的content-length标头。在这种情况下，一些前端服务器会在生成的 HTTP/1 请求中简单地复用此值。

该规范规定，HTTP/2 请求中的任何content-length标头值，都必须与内置机制计算的长度相匹配，但在降级之前，这并不总是得到正确验证。因此，也许能够注入误导性的content-length标头来走私请求。虽然前端会使用隐式的 HTTP/2 长度来确定请求的结束位置，但使用 HTTP/1 的后端必须引用派生的Content-Length标头，从而导致两端不同步。

前端 (HTTP/2)

:method POST
:path /example
:authority vulnerable-website.com
content-type application/x-www-form-urlencoded
content-length 0

GET /admin HTTP/1.1 Host: vulnerable-website.com Content-Length: 10

x=1

后端 (HTTP/1) 

POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Content-Length: 10

x=1GET / H

提示

在执行某些请求走私攻击时，你可能希望 把受害请求中的标头 附加到你的走私前缀中。但是，在某些情况下，这样可能会干扰你的攻击，从而导致标头重复等错误。在上面的示例中，我们在走私前缀中包含一个尾随参数和Content-Length标头来缓解这种问题。通过使用略长于正文的Content-Length标头，受害者的请求仍然会被附加到你的走私前缀，但会在标头之前被截断。

# 2.4H2.TE漏洞

分块传输编码与 HTTP/2 不兼容，该规范建议你对任何transfer-encoding: chunked标头执行剥离操作或完全阻止请求。如果前端服务器未能做到这一建议，并且随后对支持分块编码的 HTTP/1 后端请求进行了降级，那么这也可能导致请求走私攻击。

前端 (HTTP/2)

:method POST
:path /example
:authority vulnerable-website.com
content-type application/x-www-form-urlencoded
transfer-encoding chunked

0

GET /admin HTTP/1.1 Host: vulnerable-website.com Foo: bar

后端 (HTTP/1) 

POST /example HTTP/1.1
Host: vulnerable-website.com
Content-Type: application/x-www-form-urlencoded
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
Host: vulnerable-website.com
Foo: bar

如果网站容易受到 H2.CL 或 H2.TE 请求走私的影响，则你可以利用此行为，来执行我们在之前的请求走私实验室中介绍的相同攻击。

# 2.5隐蔽的HTTP/2支持

浏览器和其他客户端（包括 Burp）通常只会使用 HTTP/2 与服务器进行通信，这些服务器将 ALPN 作为 TLS 握手的一部分来显式地通告支持它。

有些服务器支持 HTTP/2，但由于配置错误而无法正确声明。在这种情况下，服务器看起来好像只支持 HTTP/1.1，因为客户端默认将其作为回退选项。因此，测试人员可能会忽略可行的 HTTP/2 攻击面，从而错过协议级问题，例如我们上面介绍的基于 HTTP/2 降级的请求走私示例。

想要强制 Burp Repeater 使用 HTTP/2，以便你可以手动测试此类错误配置，请执行以下操作：

  1. 从 “Settings” 对话框中，转到 “Tools” > “Repeater”。
  2. 在 “Connections” 下，启用 “Allow HTTP/2 ALPN override” 选项。
  3. 在 Repeater 中找到 Inspector 面板并展开 Request attributes 部分。
  4. 使用开关将 “Protocol” 设置为 “HTTP/2”。Burp 现在将使用 HTTP/2 发送此选项卡上的所有请求，无论目标服务器是支持 HTTP/2。

笔记

如果你使用的是 Burp Suite Professional (opens new window)，则 Burp Scanner (opens new window) 会自动检测 “隐蔽的HTTP/2支持” 实例。

# 3响应队列投毒

响应队列投毒是一种强大的请求走私攻击，可以让你窃取针对其他用户的任意响应，从而危及他们的帐户甚至整个站点。

# 4通过CRLF注入实现请求走私

即使网站采取措施，防止了基本的 H2.CL 或 H2.TE 攻击，例如验证content-length或剥离任何transfer-encoding标头，HTTP/2 的二进制格式也提供了一些新颖的方法，来绕过这些类型的前端措施。

有时在 HTTP/1 中，你可以利用服务器处理独立换行符（\n）时的差异，来走私被禁止的标头。如果后端服务器将其视为分隔符，但前端服务器不这样做，则这些前端服务器根本无法检测到第二个标头。

Foo: bar\nTransfer-Encoding: chunked

在处理完整的 CRLF（\r\n）序列时不存在这种差异，因为所有 HTTP/1 服务器都认为这会终止标头。

另一方面，由于 HTTP/2 消息是二进制的而不是基于文本的，因此每个标头的边界都基于显式的、预先确定的偏移量，而不是分隔符。这意味着\r\n在标头值中不再具有任何特殊意义，因此可以包含在值本身中，而不会导致标头被拆分：

foo bar\r\nTransfer-Encoding: chunked

这本身看起来相对无害，但当它被重写为 HTTP/1 请求时，\r\n将再次被解释为标头分隔符。因此，HTTP/1 后端服务器将看到两个不同的标头：

Foo: bar
Transfer-Encoding: chunked

# 5HTTP/2请求拆分

在我们介绍响应队列投毒 (opens new window)时，你学习了如何在后端将单个 HTTP 请求拆分为两个完整的请求。在我们看到的示例中，拆分发生在消息正文的内部，但是在 HTTP/2 降级过程中，你也可以使拆分发生在标头中。

这种方法更为通用，因为你不需要依赖于 允许包含正文 的各种请求方法。例如，你甚至可以使用GET请求：

:method GET
:path /
:authority vulnerable-website.com
foo

bar\r\n \r\n GET /admin HTTP/1.1\r\n Host: vulnerable-website.com

在content-length得到充分验证 且 后端不支持分块编码的情况下，这非常有用。

# 5.1前端重写核验

若要在标头中拆分请求，你需要先了解前端服务器是如何重写请求的，并在手动添加任何 HTTP/1 标头时考虑这一点。否则，拆分出来的其中一个请求可能会缺少必需标头。

例如，你需要确保后端接收到的两个请求都包含Host标头。前端服务器通常会在降级期间剥离:authority伪标头，并将其替换为新的 HTTP/1 Host标头。有不同的方法可以执行此操作，这可能会影响你注入的Host标头位置。

请考虑以下请求：

:method GET
:path /
:authority vulnerable-website.com
foo

bar\r\n \r\n GET /admin HTTP/1.1\r\n Host: vulnerable-website.com

在重写过程中，某些前端服务器会将新的Host标头追加到当前标头列表的末尾。就前端的 HTTP/2 而言，这是在foo标头之后。请注意，这也是在后端拆分请求的位置之后。这意味着第一个请求根本没有Host标头，而走私的请求将会有两个标头。在这种情况下，你需要定位注入的Host标头，以便在拆分发生后，使它最终出现在第一个请求中：

:method GET
:path /
:authority vulnerable-website.com
foo

bar\r\n Host: vulnerable-website.com\r\n \r\n GET /admin HTTP/1.1

你还需要以类似的方式，对注入的任何内部标头进行位置调整。

在上面的示例中，我们通过响应队列投毒 (opens new window)的原理拆分了请求，但你也可以通过这种方式，为经典的请求走私攻击 走私前缀。在这种情况下，注入的标头可能会与 后端附加到前缀请求中的标头 发生冲突，从而导致标头重复错误 或 导致请求在错误的位置终止。为了缓解这种情况，你可以在走私的前缀后面添加正文参数，以及略长于正文的Content-Length标头。受害者的请求仍然会被附加到你的走私前缀中，但会在标头之前被截断。

# 6HTTP请求隧道

到目前为止，我们介绍过的许多 请求走私攻击 之所以成为可能，是因为前端和后端服务器 复用同一个连接来处理多个请求。HTTP 请求隧道提供了一种构建高严重性漏洞的方法，即使在根本没有复用连接的情况下也能够实现。
